# 공시·수급 자동 수집과 모의운용 검증 — 2026-10-13

공시와 수급 자료를 정기적으로 수집하고, 주문 계획부터 체결까지 가격 차이와 비용을 기록하도록 했다. 모의운용 성과는 검증 기준을 미리 정한 뒤 새로 쌓이는 종가로 평가한다. 필요한 관측 기간이 지나기 전에는 수익성이 검증됐다고 판단하지 않는다.

## 자동 실행과 저장

- 기존 일일 `main.py --mode rebalance`의 주문·종가 처리 이후, 상시 스케줄러의 장마감 처리 이후에 별도 연구 프로세스를 시작한다. `--dry-run`에서는 시작하지 않는다.
- `core/research_operations.py`가 가격, 공시·수급, 모의 검증 도구를 각각 제한 시간 안에서 실행한다. 중복 실행을 막고, 장중과 장마감 수집을 구분해 오전 수집 때문에 오후 작업이 빠지지 않게 했다. 같은 구간에서 실패한 작업을 자동으로 재시도할 때는 60분 간격을 둔다.
- 일부 수집 실패·갱신 지연은 상태 JSON뿐 아니라 CLI 종료 코드 1로도 알려 외부 실행기가 성공으로 오인하지 않게 한다.
- 공급자 지연이 주문 처리를 기다리게 하지 않는다. 각 작업의 시작·종료·실패·자료 상태를 `data/research_operations/`에 기록한다. 자식 프로세스가 중단되거나 기록이 오래되면 화면에서 확인할 수 있다.
- `config/research_operations.yaml`에서 활성화·제한 시간·재시도·여유 공간 기준을 관리한다. 저장 위치의 여유가 256MiB 미만이면 수집을 보류한다. `QUANT_RESEARCH_AUTOMATION_DISABLED=true`는 자동 수집을 끈다.
- 기존 운영 프로세스의 연결 외에, 아래 일일 종가·수집 점검을 별도로 사용한다. PC가 꺼져 있거나 실행 앱이 꺼져 있으면 로컬 자료는 쌓이지 않는다. 별도 OS 예약 작업을 설치하거나 새 전략의 매매를 켜지 않는다.

## 공시와 수급

`core/market_intelligence.py`와 `tools/market_intelligence.py`는 현재 관찰 대상으로 설정한 국내 주식 9종목을 수집한다.

**공시:** OpenDART 기업 고유번호와 공시 목록을 조회한다. 페이지 수·행 수·대상 회사를 검증하며, 정상적인 공시 없음과 인증 실패·시간 초과·일부 페이지만 수집된 상태를 구분한다. 접수번호, 보고서명, 접수일, 정정·철회 표시와 원문 링크를 저장한다. 접수일만으로 정확한 발표 시각이나 정정 전 본문을 만들지 않는다. 현재 구현의 원문 보존 범위는 API 응답 필드이며 공시 본문 ZIP 전체 보관은 포함하지 않는다. [OpenDART 공시검색](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)

**수급:** NAVER 증권 공개 웹 응답의 개인·기관·외국인 순매수 **수량(주)** 을 보관한다. 당일 값을 제외한 최근 완료 거래일을 대상으로 한다. 거래대금, KRX 계약 원본, 시장 전체 수급, 거래소별 집계 범위로 확대 해석하지 않는다. 공개 웹 인터페이스 변경 시 정상 자료로 대체하지 않고 수집 실패로 표시한다.

각 기록에 공급자의 기준일과 시스템이 실제로 본 시각을 별도로 둔다. 같은 자료의 내용 변경은 새 버전으로 보존한다. `output/market_intelligence/latest.json`은 최신 상태, `snapshots/`와 `versions/`는 관측 근거다. 이 두 원장은 장기 검증에 필요한 자료이므로 임시 캐시로 삭제하지 않는다.

실수집에서 수급 **9/9종목 × 4거래일 = 36행**을 확인했다. 현재 DART 설정 키에는 서버가 **010(미등록 키)** 을 반환했다. 사용자 결정에 따라 키는 나중에 갱신하며, 인증 실패가 있는 현재 전체 상태는 `partial`이다. `.env`의 `DART_API_KEY`를 유효한 키로 바꾼 뒤 수집 도구를 다시 실행하면 된다. 키 원문은 보고서·로그·명령 인자로 출력하지 않는다.

## 체결비용 관측

`core/execution_analytics.py`를 바스켓 주문 계획, 실제 주문 실행, 주문 상태 저장과 체결 재조회에 연결했다. `execution_cost_events`는 관측 이벤트를 추가하는 테이블이다. 보고 도구는 SQLite를 읽기 전용으로 열며, 누락된 테이블을 조회 과정에서 만들지 않는다. 새 테이블은 기존 운영 초기화·마이그레이션 경로에서 생성된다.

- 바스켓 계획 가격·시각이 있으면 그 기준을 전달한다. 다른 호출은 실행부에 입력된 가격이라는 사실을 명시한다. 옛 주문의 의사결정 가격을 추정해 채우지 않는다.
- 매수 비용은 `(체결가 − 기준가) × 체결수량`, 매도 비용은 부호를 반대로 계산한다. 가격 비용과 수수료·세금을 구분하고, 체결가에 이미 반영된 슬리피지를 다시 더하지 않는다.
- 부분 체결과 재조회는 주문의 최신 누적 상태로 계산하므로 같은 체결을 여러 번 합산하지 않는다. 거부·미체결 시도도 관측한다.
- 통화, 모의 장부·증권사 환경, 기준가격 종류, 체결가격 근거, 비용 근거를 나눠 집계한다. 증권사 체결가격을 확인했더라도 수수료·세금이 추정치라면 전체 비용을 실측이라고 표시하지 않는다.
- 관측 시각은 로컬 시스템의 시각이다. 독립적인 주문 도착가격, 거래소의 정확한 체결 시각, 잔량 평가 종료가격을 모두 확보한 완전한 비용 분해는 아니다. 미체결 잔량의 기회비용은 `null`로 남긴다.

이 구분은 결정가격 대비 체결·지연·기회비용을 구별하는 [CFA의 거래 집행 기준](https://www.cfainstitute.org/insights/professional-learning/refresher-readings/2026/trade-strategy-execution)을 따른 설계다. 현재 확보하지 못한 항목까지 측정했다고 주장하지 않는다.

## 장기 모의 검증

`config/paper_validation.yaml`에 검증 기준을 먼저 고정한다. 기본 요건은 **동일 거래일 비교가 가능한 일간 수익률 120개, 관측 기간 180일, 비교지수 상승일·하락일 각각 20개, 결측 비율 5% 이하**다. 연구 표본의 최소 요건이며 수익성 합격 기준이나 실계좌 승인 조건이 아니다.

`core/paper_validation.py`는 활성 바스켓별 운용 코드·설정·노출 정책·비교지수 지문과 등록 시각을 추가형 원장에 기록한다. 기존 스냅샷·종가를 새 전진 검증 일수로 바꾸지 않는다. 운용 정책이나 코드가 바뀌면 과거 기록을 보존하고 새 검증 묶음을 시작한다. 화면·문서만 변경한 경우에는 검증 기간을 다시 시작하지 않는다.

- 등록 후 실제 측정된 종가만 인정하며, 뒤늦은 대량 소급 입력으로 누락을 지우지 못하도록 수집 지연을 제한한다.
- 같은 날짜의 비교지수와 입출금 조정 수익률, 관측 최대낙폭, 상승·하락일 성과, 비용, 회전, 결측을 함께 기록한다.
- 저장된 TWR은 입출금을 구간 시작에 반영하는 장부 근사치다. 정확한 현금흐름 시점별 평가를 요구하는 [GIPS 수익률 원칙](https://www.gipsstandards.org/standards/gips-standards-for-firms/gips-standards-handbook-for-firms/)과 차이가 있으며 GIPS 준수·인증 성과로 부르지 않는다.
- 비교지수는 배당 제외 가격지수다. 현금·방어 자산 비중이 다른 계좌와의 수익률 차이를 위험조정 알파로 부르지 않는다. 비용은 NAV에 이미 반영돼 재차 차감하지 않는다.
- 읽기 전용 장부의 과거 행이 수정·누락되거나 자료가 늦어지면 무결성 문제로 표시한다. 자료 부족이나 표본 요건 충족이 자동 실계좌 승격으로 이어지지 않는다.

## 코드 변경 이후의 누적 성과와 버전 비교 (2026-10-21)

운용 코드가 바뀌어도 **계좌 전체의 누적 성과는 이어서 조회**한다. `paper_validation status`와 운영 대시보드는 전체 누적 성과, 종료된 버전을 포함한 버전별 성과, 변경 전후 비교를 함께 보여준다. 현재 버전의 전진 검증 표본과 전체 운용 이력은 따로 관리한다. 기존 이벤트를 수정하거나 과거 종가를 새 버전의 표본으로 소급 등록하지 않는다.

`core/paper_performance.py`는 해시 검사를 통과한 기존 관측 기록에서 조회용 보고서를 계산한다. 이 모듈과 화면·CLI 변경은 운용 코드 지문에 포함되지 않으므로 이번 표시 기능 추가로 검증 묶음을 다시 시작하지 않는다. 보고서의 `report_version`은 조회 계산 방식의 버전이며, 검증 프로토콜이나 매매 정책의 버전과 구분한다.

- 같은 계좌·원천 DB·계산 방식·초기자본의 인접 거래일만 연결한다. 직접 종가 방식은 직전 종가 ID·해시·시각, 입출금 조정 TWR 비율, 누적 거래·입출금 원장 해시가 이어지는지도 확인한다. 저장 당시 평가에 원장 오류가 있었다면 정상 성과로 연결하지 않는다.
- 연결이 불명확하거나 중간 종가가 빠졌으면 전체 기간 수익률은 표시하지 않고, 근거가 있는 연속 구간만 나누어 보여준다. 동일 날짜 중복은 표본을 늘리지 않으며 서로 다른 원장 값이 충돌하면 해당 날짜와 인접 수익 구간의 집계를 보류한다.
- 비교지수의 종목·계산 기준·제공처가 달라지거나 날짜가 맞지 않으면 전체 비교지수 수익률과 차이는 표시하지 않는다. 확인 가능한 계좌 수익률은 별도로 유지한다.
- 변경 전 마지막 종가부터 변경 후 첫 종가까지의 수익률은 **변경 경계 구간**으로 표시하고 전체 누적 성과에만 포함한다. 어느 한 버전의 성과나 개선 효과로 귀속하지 않는다. 새 버전 첫 관측의 빈 거래 목록을 경계 비용 0원으로 해석하지 않는다.
- 변경 전후 비교는 이전 버전의 마지막 N개 수익 구간과 이후 버전의 첫 N개 수익 구간을 사용한다. N은 양쪽에서 확인되는 연속 구간 수 중 작은 값이다. 경계 구간은 제외하며, 비교할 구간이 없거나 연결 기준을 확인하지 못하면 수치를 보류한다. 기간이 같아도 시장 상황은 다르므로 변경 효과나 통계적 우열을 뜻하지 않는다.

수익률은 기존 장부의 입출금 조정 TWR 지수를 비율로 연결하며 단순 합산하지 않는다. 구간별 수익률을 기하 연결한다는 계산 원리는 [CFA Institute의 GIPS 계산 기준](https://www.gipsstandards.org/standards/gips-standards-for-firms/gips-standards-handbook-for-firms/)을 참고했다. 현재 장부는 입출금을 구간 시작으로 간주하는 근사치이며 GIPS 준수 성과라는 뜻은 아니다. 이 조회는 저장 당시 관측의 연결을 확인하며 현재 운영 DB를 다시 감사하거나 변경하지 않는다.

2026-10-21 저장 자료에서 두 바스켓 모두 기존 6개와 새 버전 1개를 합친 **종가 7개·수익 구간 6개**를 확인했다. 10월 13~21일 누적 TWR은 `kr_diversified_hold` -1.45905727%, `kr_pocket` -1.43007355%다. 새 버전 내부 수익 구간은 아직 0개이므로 변경 전후 비교와 수익성 판정은 보류한다. 최종 검증 자료는 `output/paper_performance_review_20261021/`에 보존한다.

Python 관련 검사 108개(기존 수집·검증 82개, 누적 성과 26개), JavaScript 45개를 통과했다. 운영 DB와 기존 이벤트 69개는 조회 전후 해시가 같았다. 실제 브라우저에서 누적값·종료 버전·비교 보류 표시와 폭 390px의 요약 화면을 확인했다. 브라우저 창 최소화로 스크린샷은 남기지 못했으며 화면 구조·표시 문구 검증과 구분한다. 자동 갱신 후 계좌별 펼침 상태 보존도 검사했다.

## 실행 명령

프로젝트 루트 PowerShell에서 실행한다. 수집 도구는 운영 장부에 주문이나 입출금을 기록하지 않는다.

```powershell
# 전체 관측 작업: 같은 날 재시도까지 직접 요청하려면 --force
.venv/Scripts/python.exe tools/research_operations.py --force
.venv/Scripts/python.exe tools/research_operations.py --status

# 개별 수집·조회
.venv/Scripts/python.exe tools/market_intelligence.py
.venv/Scripts/python.exe tools/paper_validation.py collect
.venv/Scripts/python.exe tools/paper_validation.py status --json
.venv/Scripts/python.exe tools/execution_cost_report.py --mode paper --limit 200
```

`QUANT_MARKET_INTELLIGENCE_DIR`, `QUANT_PAPER_VALIDATION_DIR`, `QUANT_RESEARCH_OPERATIONS_DIR`로 관측 저장 위치를 격리할 수 있다. 체결비용은 `--db`, 모의 검증은 `--db-path`로 **기존 DB 사본**을 지정할 수 있다. 대시보드의 시장 관찰 아래에서 자동 수집·공시·수급·체결비용·장기 검증 상태를 읽는다.

## 실제 일일 운영 연결 후속 점검

2026-10-13의 실제 운영 원장을 읽기 전용으로 확인했다. 오전 10:07 리밸런싱과 11:00·14:00 결측 재시도를 위한 기존 Claude 예약 지침은 있지만, 종가 확정 후의 전용 기록 예약은 없었다. 당일 장중 스냅샷은 두 바스켓에 84개·62개 있으나 `portfolio_valuations`는 0행이었다. 이전 수집 연결만으로 종가 성과가 누적된다고 볼 수 없었다.

### 수정한 누락 경로

- 오전 수집 성공이 같은 날의 장마감 수집을 막지 않도록 장중/마감 확정 후/휴장일 실행을 구분했다. DART 실패 때 이미 준비된 가격 자료를 반복 다운로드하지 않는다.
- 저장 자료가 주말·연휴 동안 36시간을 넘었다는 이유만으로 늦었다고 판단하지 않는다. 실제 필요한 거래일과 마감 후 실행 여부를 확인한다. 레이더·수급의 당일 잠정 값 제외 정책은 유지하므로 다음 날 아침에도 수집한다.
- `tools/collect_basket_closes.py`는 매매 없이 paper 계좌의 실제 원장과 정확한 종가로 별도 평가를 추가한다. 최초 종가를 새 수익률의 기준으로 삼으며 과거 장중 스냅샷을 종가로 꾸미지 않는다. 장전·장중·휴장일에는 DB를 읽기 전용으로 확인하고 직전 완료 거래일의 종가 누락을 별도로 보고한다. 현재 보유 수량만으로 놓친 과거 종가를 자동 재구성하지 않는다.
- 실제 조회에서 FDR/Yahoo의 KOSPI·KOSPI 200 최신 기준일이 실패했다. 검증 전용 비교지수를 NAVER 공개 지수 자료로 고정하고, 공급자와 코드 지문을 검증 기준에 포함했다. 공급자 응답에 오늘 잠정 값이 있어도 날짜·마감 확정 시각 검사를 통과한 값만 관측한다. NAVER 웹 자료이며 KRX 계약 원본으로 표시하지 않는다.
- `tools/daily_observation.py`가 종가 기록 → 연구 자료 수집 → 모의 검증 순서로 실행한다. 한 단계 실패가 다른 단계의 확인을 막지 않으며, 중복 실행 잠금과 전체 15분 제한을 둔다. 시간 초과 시 이번 실행이 만든 자식 프로세스 트리까지 종료한다. 저장 공간이 256MiB 미만이면 수집을 보류한다.

### 실행과 점검

